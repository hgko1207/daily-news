## Problem Statement

Claude Desktop 스케줄러가 매일 약 10:08 KST에 6개 카테고리 브리핑(`01_국내경제` ~ `06_말씀`)을 `<카테고리>/YYYY-MM-DD.md`로 커밋한다. 2026-07-01부터 약 100일, 2.2MB(1년이면 약 8MB)가 쌓였다. 지금은 GitHub 웹에서만 볼 수 있고 README는 한 줄뿐이다.

원하는 것:
1. 저장소가 무엇이고 어떻게 돌아가는지 설명하는 README
2. 폰(iOS + Android)에서 앱처럼 보는 PWA. 오늘 브리핑을 깔끔하게 보고, 이전 브리핑을 보고, 주제(카테고리, 종목·키워드)별로 모아 보고, 검색할 수 있어야 한다.
3. 앱 안 설정/안내 메뉴에서 설치 방법을 볼 수 있어야 한다.
4. 디자인은 원티드 디자인 시스템(Montage)으로 시작하고, 나중에 디자인 스킬로 다듬는다.

## What Makes This Cool

- 매일 아침 아무것도 하지 않아도 폰 홈 화면 아이콘 안에 새 브리핑이 들어와 있다. 스케줄러 커밋 → 자동 빌드 → 자동 배포.
- 100일 넘게 쌓인 아카이브가 "삼성전자 얘기가 언제, 몇 번 나왔고 그때 뭐라고 했나" 같은 질문에 답하는 개인 데이터베이스가 된다.
- 내용을 만드는 쪽(Claude 프롬프트)과 보여주는 쪽(앱)을 둘 다 내가 쥐고 있다. 앱이 원하는 구조를 소스에서 바로 내보낼 수 있다(v2 사이드카).
- v2: 브리핑이 스스로를 채점한다. "10/8 삼성전자 영업이익 컨센서스 108.1조" 같은 예측을 `claims[]`로 남기고, 날짜가 지나면 실제 값과 비교한다.

## Constraints

- 개인용 사이드 프로젝트. 비용 0원, 운영 손대지 않기.
- 서버·DB·푸시 알림 없음(v1).
- iOS Safari와 Android Chrome 모두 지원.
- 카테고리 폴더(01~06)는 스케줄러 전용. 앱 작업이 스케줄러 커밋을 깨면 안 된다.
- 마크다운 포맷은 날마다 조금씩 흔들린다. 예: `## 🔎 핵심` / `## 🔎 핵심 한두 줄`, `## 📊 지수 스냅샷 (라벨 명시)`, 7월 초 파일은 `요약:` 라벨 없음. `06_말씀`은 8/19부터, `05_투자`는 7/10부터 시작.
- Montage(`@wanteddev/wds`)는 React 18/19 + Emotion 기반이고 **GitHub Packages 레지스트리**(`@wanteddev:registry=https://npm.pkg.github.com/`)로 배포된다. 공개 패키지여도 설치에 인증 토큰이 필요하다. `@wanteddev/wds-*` 패키지는 모두 같은 버전으로 설치해야 한다. Pretendard 폰트를 CDN으로 불러와야 한다.

## Premises (합의됨)

1. 서버·DB 없는 정적 PWA. 푸시는 v1에서 제외. iOS/Android 모두 "홈 화면에 추가" + 앱 내 설치 안내 화면.
2. 마크다운 파일이 유일한 원본이고 앱은 읽기 전용. 빌드할 때 md → JSON으로 변환한다.
3. 스케줄러 push → GitHub Actions 자동 빌드 → GitHub Pages 배포. 사람 손은 필요 없다.
4. 레포가 이미 public이므로 사이트도 public이어도 된다(비밀번호 없음).
5. Montage를 쓰기 위해 Vite + React SPA로 만든다. CI에 GitHub Packages 읽기 토큰을 설정한다.
6. 앱 코드는 같은 레포의 `app/`에 둔다. 카테고리 폴더는 스케줄러만 건드린다.
7. (2차 의견 반영, 수정) 액션·종목·일정 모아보기는 v1에서 **느슨한 파서**로 뽑는다. 약 1주 실제로 써 본 뒤에 스케줄러 프롬프트를 고쳐 `data/YYYY-MM-DD.json` 사이드카(+`claims[]`) 스키마를 확정한다.

## Cross-Model Perspective (Claude subagent)

- **가장 멋진 버전:** "브리핑이 스스로 채점되는 앱". 사이드카에 `claims[]`(날짜·대상·예상값)를 넣고 날짜가 지나면 실제 결과를 기록해 "지난주 브리핑이 맞췄나?" 카드를 띄운다. 액션은 체크박스로 만들고 완료 상태는 localStorage에 저장한다. 종목별 언급 타임라인을 둔다.
- **핵심 신호:** 프롬프트까지 바꾸겠다는 결정은 사용자가 원하는 것이 단순한 읽기 앱이 아니라 날짜를 가로지르는 구조화 데이터, 즉 개인 대시보드라는 뜻이다.
- **50% 해결 도구:** Quartz v4는 참고만 한다(React가 아니고 문서 사이트형 UX). PWA는 vite-plugin-pwa, 검색은 MiniSearch(→ Eng Review에서 부분문자열 스캔으로 변경).
- **반박:** 사이드카 스키마는 써 본 뒤에 정해야 한다 → 전제 7로 반영. 첫 주말에는 Montage를 빼자 → **채택하지 않음.** 인증은 `read:packages` PAT로 해결하고(배포 섹션 참고), 1시간짜리 스파이크로 가장 먼저 검증한다.

## Approaches Considered

### Approach A: 런타임 마크다운 뷰어
jsDelivr/raw에서 md를 직접 fetch해 렌더한다. 노력 S, 위험 낮음. 검색과 모아보기가 사실상 불가능해서 원하는 기능의 1/3만 충족한다.

### Approach B: 빌드타임 데이터 파이프라인 + Montage PWA (선택)
push될 때마다 md → JSON(인덱스, 일자별, 검색, 집계)을 만들고, Vite + React + `@wanteddev/wds` + vite-plugin-pwa로 빌드해 Pages에 배포한다. 노력 M(사람 약 1~2주, CC 약 1~2일, 여러 세션), 위험 중간(패키지 인증, 파서 유지보수).

**v1 범위:** 오늘, 상세, 지난 브리핑(달력), 검색, 모아보기(액션·종목), 설정(설치 안내·테마·데이터 정보), PWA, 자동 배포.
**v1.1로 미룸:** 모아보기의 일정 탭, 글자 크기, 카테고리 순서 변경, 다른 카테고리의 종목 교차 언급.
**v2:** 사이드카 JSON + `claims[]` 채점.

### Approach C: Astro + Pagefind, Montage는 토큰만
가장 빠르고 검색도 강하다. 하지만 원티드 컴포넌트를 쓸 수 없어 "앱 느낌"이 약하고, 모아보기는 따로 구현해야 한다.

## Recommended Approach: B

사용자가 원한 세 가지(깔끔히 보기, 이전 것 보기, 주제별 모아보기)와 Montage를 동시에 만족하는 유일한 안이다. "주제별 모아보기"와 "검색"은 같은 메커니즘(전체 파일을 미리 읽어 만든 인덱스)이라서 B 하나로 둘 다 해결된다.

### 카테고리 매핑 (`parse.ts` 안)

| 폴더 | slug | 라벨 | 이모지 |
|---|---|---|---|
| 01_국내경제 | economy | 국내·경제 | 🇰🇷 |
| 02_글로벌기술 | global | 글로벌 기술 | 🌐 |
| 03_개발자 | dev | 개발자 | 👨‍💻 |
| 04_교양생활 | life | 교양·생활 | 🌱 |
| 05_투자 | invest | 투자 | 📈 |
| 06_말씀 | word | 오늘의 말씀 | 📖 |

글로브 패턴은 `0[0-9]_*/[0-9]{4}-[0-9]{2}-[0-9]{2}.md`이다. 매핑에 없는 새 폴더가 생기면 폴더명을 그대로 라벨로 쓰고 빌드 경고만 낸다(실패시키지 않음).

### 데이터 파이프라인 (`build-data.ts`)

파서 원칙은 **"원문은 항상 보여준다, 구조 추출은 보너스"**이다. 추출에 실패해도 그 날짜의 마크다운 원문 렌더링은 반드시 된다.

출력 파일 (`app/public/data/`):

1. `index.json`: 날짜 목록과 날짜별 카테고리 요약
   ```ts
   type Index = {
     generatedAt: string;          // ISO
     latestDate: string;           // 'YYYY-MM-DD'
     days: { date: string; categories: { slug: string; title: string; highlights: string[] }[] }[];
   };
   ```
2. `days/YYYY-MM-DD.json`: 하루치 전체
   ```ts
   type Day = { date: string; entries: { slug: string; title: string; highlights: string[]; markdown: string }[] };
   ```
3. `search.json`: 검색 코퍼스(Eng Review D3에서 MiniSearch 대신 **부분문자열 스캔**으로 확정). 단위는 "항목"(`##`/`###` 섹션 하나)이고, `text`는 헤딩 + 본문 최대 200자다. 클라이언트는 검색어를 공백으로 나눠 **모두 포함(AND)**하는 섹션을 `String.includes`로 찾아 최신순 최대 100개를 보여준다. 입력 후 200ms 디바운스. 한국어 조사가 붙은 단어("삼성전자는")나 단어 중간("전자")도 찾을 수 있다.
   ```ts
   type SearchDoc = { id: string; date: string; slug: string; heading: string; text: string };
   ```
   검색 탭에 처음 들어갈 때 lazy-load한다. 예상 크기는 1년치 gzip 기준 약 1MB 이하이다. 빌드할 때 크기를 출력하고, 비압축 3MB를 넘으면 반기 단위 파일로 나누고 최근 파일부터 로드한다.
4. `aggregates.json`: 모아보기용
   ```ts
   type Aggregates = {
     actions: { date: string; slug: string; text: string; id: string }[];        // '✅' 로 시작하는 줄/불릿
     tickers: Record<string, { name: string; code?: string; mentions: { date: string; slug: string; text: string }[] }>;
     events: { date: string; label: string; sourceDate: string }[];             // 투자 '캘린더' 표의 행
   };
   ```

추출 규칙(느슨하게, 이모지·키워드 기준):

- **제목:** 첫 `# ` 줄.
- **핵심:** `^##\s*🔎` 헤딩 아래부터 다음 `---` 또는 `##`까지의 불릿과 문단. 불릿이 없으면 문단을 문장 단위로 나눈다. 아무것도 없으면 첫 `##` 섹션의 첫 문장으로 대체한다.
- **액션:** `✅` 가 포함된 **불릿 줄만**(헤딩 줄 `## ✅ …` 자체는 제외)(`- ✅ **액션:** …`, `## ✅ 액션 포인트` 아래 불릿). id는 `date+slug+hash(text)`로 만든다(체크 상태를 localStorage에 저장할 키).
- **종목:** `05_투자`의 **`^##\s*⭐` 로 시작하는 헤딩 아래 블록에서만**(실측 헤딩 변형 10가지: `관심 종목`, `관심 종목 촉매`, `관심 종목 (촉매 + 체크포인트)` 등) `- **이름(코드):**`, `- **이름(TICKER):**`, `- **이름:**` 패턴을 읽는다. 다른 섹션의 `- **수출:**`, `- **HBM:**` 같은 라벨 불릿은 제외한다. 키는 코드/티커다. 먼저 전체 파일을 한 번 훑어 `이름 → 코드` 매핑을 만들고, 코드가 없는 언급도 이름으로 같은 키에 합친다. 매핑이 없으면 이름을 키로 쓴다. 다른 카테고리에서 같은 이름이 나오면 mention으로 추가하는 건 v1.1로 미룬다(오탐 위험).
- **일정:** `05_투자`의 `^##\s*🗓` 로 시작하는 헤딩 아래 표에서 `| 날짜 | 이벤트 |`를 읽는다.
  - 연도 결정: sourceDate의 연도를 붙이되, (sourceDate 월 − 이벤트 월)이 6 이상일 때만 다음 해로 본다. 예: 12월 파일의 `1/15` → 다음 해, 10/1 파일의 `9/30` → 같은 해.
  - 표기 정규화: `10/8(목) 새벽 3시` → 10/8. `10/27~28` → 시작일 10/27. `10월 말`처럼 파싱되지 않는 표기는 `label`에 원문을 남기고 "날짜 미정" 그룹에 넣는다.
  - 중복 처리: 문구가 날마다 바뀌어 문자열로 중복을 제거할 수 없다. 그래서 **다가오는 일정(오늘 이후)은 캘린더 표가 있는 가장 최근 파일 1개의 행만** 쓴다. 지난 일정은 이벤트 날짜별로 그 날짜 이전 가장 최근 파일의 행만 남긴다.
- **날짜/요일:** 파일명 기준. 빌드 시점의 현재 시각은 쓰지 않는다.

품질 가드는 두 겹이다.
- **`build-data` 자체 리포트(CI, 비차단):** 파일마다 title·highlights 추출 여부를 검사한다. 실패 파일 목록과 search.json·index.json 크기를 `$GITHUB_STEP_SUMMARY`에 쓰고, `::warning::` 어노테이션을 남긴다. exit code는 0이다. 새 날짜의 포맷이 흔들려도 배포는 막히지 않는다. 0이 아닌 exit는 md 파일 읽기 실패 같은 진짜 오류에서만 낸다.
- **`vitest`(로컬 전용, `pnpm test`):** 파서 단위 테스트와 실제 저장소 파일 스냅샷을 돌린다. 배포 워크플로에서는 실행하지 않는다. 기대치: 모든 파일에 title이 있고, `06_말씀`을 제외한 파일의 95% 이상에 highlights가 있다.
- `✅ 액션`은 일부 카테고리·일부 날짜에만 있다(예: 10/6 기준 02, 04에만 있음). 모아보기의 액션 탭이 듬성듬성한 건 정상이다.

### 화면 (하단 탭 4개 + 헤더 검색)

| 탭 | 내용 |
|---|---|

### PWA

- `vite-plugin-pwa` (`registerType: 'prompt'`).
- manifest: `name: "데일리 브리핑"`, `short_name: "브리핑"`, `display: "standalone"`, `start_url`·`scope` = Pages base(`/daily-news/`), theme/background 색은 Montage 토큰, 아이콘 192/512 + maskable, iOS용 `apple-touch-icon` 180.
- 캐시 전략: 앱 셸은 precache. `data/index.json`과 `aggregates.json`은 **NetworkFirst + `networkTimeoutSeconds: 3`**(아침마다 새 데이터, 느리거나 오프라인이면 3초 후 캐시)이고, 앱은 이 둘을 `fetch(url, { cache: 'no-cache' })`로 요청한다. GitHub Pages가 `cache-control: max-age=600`을 주므로 ETag 재검증 없이는 최대 10분 지연된다(Eng Review D4). `data/days/*.json`과 `search*.json`은 **StaleWhileRevalidate**. `data/`는 서비스 워커 precache 대상에서 제외한다(기본 globPatterns 유지). Pretendard CDN은 CacheFirst.
- **새 데이터 감지와 앱 업데이트는 분리한다.** 데이터만 바뀐 배포는 서비스 워커를 바꾸지 않기 때문이다.
  - 새 브리핑: 앱이 포그라운드로 돌아올 때(`visibilitychange`) `index.json`을 다시 받아 `generatedAt`/`latestDate`가 바뀌었으면 데이터를 다시 불러오고 토스트 "새 브리핑이 도착했어요"를 띄운다.
  - 앱 코드 업데이트: vite-plugin-pwa의 `onNeedRefresh`일 때만 "앱이 업데이트됐어요 · 새로고침" 토스트를 띄운다.
- 라우팅은 GitHub Pages SPA 404 문제를 피하려고 `HashRouter`를 쓴다. 딥링크는 `/#/day/2026-10-06/invest` 형식.

### 배포 (`.github/workflows/deploy.yml`)

- 트리거: `push` to `main`(paths: `0*/**`, `app/**`, `.github/workflows/**`) + `workflow_dispatch`.
- `permissions: contents: read, pages: write, id-token: write, packages: read`
- 단계: `actions/checkout` → `pnpm/action-setup` → `actions/setup-node`(node 20+, `cache: pnpm`, `cache-dependency-path: app/pnpm-lock.yaml`) → `pnpm install --frozen-lockfile` → `pnpm build:data` → `pnpm build` → `actions/upload-pages-artifact`(`path: app/dist`) → `actions/deploy-pages`. 모든 run 스텝은 `defaults.run.working-directory: app`.

### 스케줄러와 공존

스케줄러가 로컬 작업 사본에서 commit/push한다면, 내가 `app/` 변경을 원격에 push한 뒤 스케줄러의 push가 **non-fast-forward로 거절**될 수 있다.
- 조치: Claude Desktop 스케줄러 프롬프트에 "커밋 전에 `git pull --rebase` 실행" 한 줄을 추가한다. 파일 경로가 겹치지 않으므로 충돌은 나지 않는다.
- 확인 필요: 스케줄러가 어느 경로의 작업 사본에서 도는지(이 `D:\project\Coding\daily-news`인지 별도 경로인지).
- **같은 작업 사본이면 위험:** 스케줄러가 `git add -A`나 `git add .`를 쓰면 작업 중인 `app/` 파일까지 커밋된다. 대책은 둘 중 하나다. (a) 스케줄러 프롬프트에서 `git add 0*/` 처럼 카테고리 폴더만 명시적으로 add하게 한다. (b) 앱 개발은 별도 클론이나 `git worktree`에서 한다. 둘 다 하는 것을 권장한다.
